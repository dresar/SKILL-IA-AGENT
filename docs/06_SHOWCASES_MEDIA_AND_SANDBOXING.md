# Showcases, Media Storage, and Preview Isolation

## 1. Main principle

A skill preview must demonstrate the skill's value honestly and safely. A static screenshot is not a live demo. A locally built example is not an upstream author's official output. A live URL is not verified merely because it loads. Label the type and status clearly.

The application must never evaluate arbitrary skill instructions, run arbitrary imported scripts, or install dependencies from untrusted sources in the primary web application's process. A skill may contain operational instructions for an AI agent; that does not make those instructions trusted or safe for SkillCanvas to execute.

## 2. Showcase types

Support a typed union such as:

- `image_gallery`: ordered screenshots/illustrations.
- `live_demo`: external HTTPS URL allowed through an explicit embed/open policy.
- `static_demo`: built static output hosted from an isolated preview origin.
- `video`: hosted video with a poster/fallback and accessible controls.
- `sample_output`: rendered sample artifact, optionally paired with sample input.
- `workflow`: step-by-step visual explanation of a skill workflow.
- `documentation`: markdown or structured documentation excerpt.
- `unavailable`: honest state explaining why an interactive preview is not present.

Do not add custom JavaScript fields to a database showcase record. Keep executable code in reviewed, version-controlled demo projects and deploy the output separately.

## 3. Preview evidence labels

Use explicit labels that match actual status:
- **Live demo** — a remote interactive destination that has been checked according to the configured process.
- **Static showcase** — a locally rendered or prebuilt example; not necessarily generated by the upstream skill.
- **Screenshot** — a static image only.
- **Sample output** — an example result with an indication of source/context.
- **Source preview** — a text view of a source file.
- **Not available** — no preview currently exists.

Optional verification states should be narrow: URL reachable on date, expected content observed, screenshot captured, or demo build passed. Do not use a generic safety badge without a real security review process.

## 4. Isolated live demo architecture

Preferred order:
1. Curated prebuilt static demo on a separate origin controlled by the project.
2. External trusted demo embedded only when the host intentionally permits embedding and its origin is allowlisted.
3. External link opened separately when embedding is not safe/possible.
4. Screenshot or sample artifact fallback.

A live demo should not share the main application's origin, cookies, local storage, service workers, or privileged endpoints. Use a distinct site/origin such as a dedicated preview subdomain or a properly isolated deployment origin. The exact domain is a deployment decision.

For iframe use:
- Set the narrowest sandbox flags needed by the demo. Do not reflexively combine `allow-scripts` and `allow-same-origin` for untrusted content.
- Add an explicit `allow` policy only for features that are required.
- Set `referrerPolicy` conservatively.
- Apply restrictive CSP headers to preview hosts, including script, connect, frame, image, style, font, form, and navigation policies as practical.
- Use `frame-src`/`frame-ancestors` policies deliberately for the parent and child.
- Disable top navigation, popups, clipboard, downloads, camera, microphone, geolocation, and other capabilities unless required and reviewed.
- Provide a safe “Open demo in new tab” action for demos that cannot be embedded, after URL validation.
- Do not forward session credentials or secrets to demo frames.
- Use a per-demo allowlist; never allow an arbitrary URL pasted into a request to become an iframe `src` without policy validation.

## 5. Build previews from source

If the product later supports automatic demo builds:
- Treat every source repository as untrusted.
- Use disposable isolated workers/containers with no production secrets and restricted network egress.
- Apply CPU, memory, execution-time, log-size, artifact-size, and concurrency limits.
- Do not mount host credentials, `.env` files, SSH keys, Docker socket, or privileged filesystem paths.
- Pin or lock dependencies and produce a build manifest.
- Do not run package install/build scripts on the web request path.
- Apply static analysis and malware/secret scanning where feasible, but do not claim scans prove a demo safe.
- Publish only the produced artifact to an isolated preview origin.
- Keep build output and logs sanitized; never expose secret-bearing environment values.
- Require manual approval before first publishing a new preview source.

Automatic source builds are not required for MVP. Admins can link externally hosted demos or attach approved static assets.

## 6. Media provider architecture

Create an `AssetStorageProvider` interface, with operations no broader than required:
- `uploadPublicAsset(...)`
- `uploadPrivateAsset(...)` if private asset support is needed
- `deleteAsset(...)`
- `getPublicUrl(...)` or return a stable provider reference
- `getMetadata(...)` if supported

Candidate implementations:
- **GitHub repository provider:** for small public, versioned screenshots and skill assets with source review. Save repo path, branch/commit/checksum, MIME, and size. Upload/update through a server-side GitHub API integration. Check current API constraints and repository limits.
- **Neon Object Storage provider:** for uploaded assets where an S3-compatible object store, public/private bucket policy, and branch-aware object model are useful. Use the current official Neon endpoint, region, credentials, and access model. Use AWS SDK/S3-compatible client behavior only as documented. Never guess signed URL generation or public URL shape.
- **No-storage mock provider:** only in tests and local UI development, clearly separated from production behavior.

Choose a default provider through validated server configuration. Do not automatically fall back to a different provider after an upload failure without telling the admin.

## 7. Upload validation

Server-side checks must include:
- Authentication and curator/admin authorization.
- Request/file count limits and per-file byte-size limits.
- Allowlist of image types actually supported (for example PNG, JPEG, WebP, AVIF if the toolchain supports it); SVG should be rejected by default or sanitized using a proven, maintained sanitizer and served with conservative policy.
- MIME/signature inspection from the file bytes; do not trust `Content-Type` or extension alone.
- Random/server-generated object names; never use a raw user filename as a storage key.
- Dimension/pixel limits to guard decompression bombs and memory exhaustion.
- Optional safe re-encoding/metadata stripping using a maintained image library.
- Alt text and intended use for published screenshots.
- Duplicate checksum detection if worthwhile.
- Rate limits and clear error states.

If animated images are supported, enforce frame count, duration, and size limits. Do not accept executable or script-like content through the image endpoint.

## 8. CDN and caching behavior

The owner prefers GitHub-backed media. Small public assets may use stable public repository URLs; do not claim that raw GitHub is a full image CDN or guarantees transformations/SLA. If cache behavior, image resizing, high throughput, or private authorization becomes a requirement, evaluate Neon Object Storage delivery or an approved CDN separately.

- Use stable, versioned filenames or content hashes for immutable assets.
- Use appropriate cache policy for immutable public assets, verified against the delivery provider's actual behavior.
- Avoid long immutable cache headers for URLs whose content can be overwritten in place.
- Use alt text from the asset metadata and specify image width/height or aspect ratio to reduce layout shift.
- Avoid loading full-resolution gallery images before needed; use appropriate sizes and lazy loading.
- Keep external remote-image configuration limited to specific trusted domains. Never set wildcard remote image hosts for convenience.

## 9. Preview fallback design

When a demo is unreachable or blocked:
- Show a stable screenshot or sample output where available.
- Display the last checked timestamp only when one was recorded.
- Explain the failure in concise text without exposing networking internals.
- Offer a retry and safe source link.
- Do not endlessly retry, poll aggressively, or block the entire skill detail page.
- Keep the rest of the skill information and command access functional.

## 10. Security test cases

- A skill with HTML/JavaScript attempting to read parent DOM cannot access the main app.
- A live URL using `javascript:`, `data:`, localhost/private IP, an unapproved protocol, or a non-allowlisted embed host is rejected.
- A preview cannot navigate the parent window unless explicitly permitted.
- Uploaded SVG/script/polyglot, oversized images, incorrect MIME, traversal-style filenames, and excessive pixel dimensions are rejected.
- Failed uploads do not create published DB asset rows that point to missing files.
- Failed DB writes do not result in the UI claiming a successful publish.
- Draft/private assets cannot be retrieved anonymously.
- Object keys and public URLs are never constructed from untrusted paths without canonical validation.
- Main app session cookies are not sent to preview origins.
